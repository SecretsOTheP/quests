Plane of Time hotfix -- Lua and manual SQL deployment

No server rebuild is required. Deploy during a break with no active Time
attempts. Do not reload quests mid-raid, including between pulls: reloading
discards the controller's in-memory encounter state.

1. Deploy the Time A and Time B Lua together from this revision. Include the
   full potimea/ and potimeb/ directories, including encounters/ and script_init.
   Also deploy lua_modules/potime_cycle.lua. Both controllers require this
   revision together: their player-count messages now identify arriving players.
   Phase1Air.lua, Phase1Earth.lua, Phase1Fire.lua, Phase1Undead.lua,
   Phase1Water.lua, and Phase2.lua already contain shadow item suppression;
   they are required even though this PR does not change those files.
2. Execute sql/2026_10_15_Time_B_Graveyard_Recovery.sql manually against the
   content database. A quest merge or reload does not execute SQL.
3. Start fresh Time A and Time B zone processes after deployment so scripts
   and the zone's graveyard timer are loaded together.

Verify the timer after executing SQL:
SELECT z.zoneidnumber, z.short_name, z.graveyard_time, z.graveyard_id,
       g.zone_id AS configured_graveyard_zone
FROM zone AS z
LEFT JOIN graveyard AS g ON g.id = z.graveyard_id
WHERE z.zoneidnumber = 223 AND z.short_name = 'potimeb';
Expected: graveyard_time 30 and configured_graveyard_zone 223. If no matching
graveyard exists, the guarded UPDATE changes nothing; inspect the configuration.

This package changes the corpse delay, not its destination. The native server
and graveyard configuration determine where corpses move. Our local TEST has
a separate native PoP-to-Tranquility routing change that is NOT included here;
do not assume that destination on another server. The tombstones separately
preserve the source guild copy when moving players between Time A and Time B.
SQL does not move existing corpses or repoint a graveyard.

Each guild has one fixed 6-day, 18-hour cycle starting on entry. Boss kills do
not extend it. At its end, the next run starts fresh with no kills or loot
restrictions carried from the previous cycle. P1's 12-hour and P2/P3's 3.5-day
loot deadlines remain shorter, capped at the cycle end. P4-P6 kills stay down
until that boundary.

Existing guild saves retain their kills and start a full cycle on first entry
after deployment. Saved god deadlines align with that new cycle end; existing
P1-P3 deadlines expire naturally. Completed P3 or a saved god kill grants the
checkpoint on adoption. Do not delete saved progress or lockouts. No SQL schema
migration is needed. D7 save retention and longer identity/cycle metadata
retention govern storage only; they cannot move the fixed gameplay deadline.

Before clearing P3, an attempt must complete P1-P3. Failure returns the attempt
to P1 after cooldown; still-locked kills return as empty-loot shadows. Clearing
P3 earns a checkpoint for the cycle. Subsequent visits clear P1, then continue
at the first unfinished phase from P4 onward without repeating P2/P3.

P4+ attempt expiry preserves bosses. In P5 it refreshes room guards for surviving
bosses and relocks those bosses until their guards are cleared. Combat defers
that refresh. P4/P6 have no static room guards to refresh. Ten minutes without
participating players closes the visit; players recovering in the graveyard
prevent that empty-zone closure. A cold restart also begins a new P1 visit.
GM shutdown and Quarm's post-kill cleanup still close visits. The cycle boundary
ends the run even during combat.

The raid cap remains 90, with 18 allowed immediately in each P1 wing. Repeated
clicks reserve only one place per character; actual arrivals and fresh player
counts reconcile those reservations.

Local #timedebug modules and recovery NPC helpers are not part of this package.
